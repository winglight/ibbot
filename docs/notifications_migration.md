# Notification Settings Migration (Redis-backed configuration)

The notification API now persists channel settings in Redis instead of the
SQLite configuration table.  Routes under `/api/notifications` interact with the
shared configuration service so that UI updates and the standalone
`notification` worker consume the same source of truth.

## Storage changes

* Notification settings are saved at `json:notification:settings` (RedisJSON
  when available, otherwise a plain JSON string).  Each record contains:
  * `settings`: the canonical channel configuration stored with event *tokens*.
  * `updated_at`: ISO timestamp generated by the API.
  * `version`: schema indicator (`2024.09`).
* A flattened copy is synchronised to the configuration hash
  `hash:config:notification` so the notification service continues to read
  boolean toggles and credentials.  The config update is broadcast to
  `pubsub:config:update` to invalidate caches.

Existing rows in `config.notification_settings` are no longer read.  To migrate
historic values run the API once; the first update will write the payload into
Redis and the worker will start consuming the new hash immediately.

## API contract updates

* `/api/notifications/settings` now responds with `{success, data, version,
  updated_at}`.  The `data` field contains the sanitised structure previously
returned as `settings`.
* `/api/notifications/settings` `PUT` returns the same envelope (`success`,
  `message`, `data`, `version`, `updated_at`).
* `/api/notify` and `/api/notifications/test` forward requests to the
  notification micro-service.  When the service endpoint is unreachable the API
  replies with `{"success": false, "message": "Notification service not enabled"}`
  instead of raising an error.

## Front-end expectations

* UI helpers now consume `response.data` when loading settings.
* Success and failure alerts display messages returned by the API or service.
* Test notification alerts highlight service failures using the new response
  envelope.

## Operational notes

* Ensure the Redis instance referenced by the UI and the notification worker is
  reachable before updating settings.
* If RedisJSON is unavailable the API automatically falls back to `SET`/`GET`.
  The worker reads the mirrored hash and does not require RedisJSON support.
